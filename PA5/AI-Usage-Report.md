#### A.2.3.1. Implementing the self-service change-password feature

| Item | Description |
| --- | --- |
| **Tool / version** | Claude Code, model `claude-sonnet-5` (Claude Sonnet 5) |
| **Access platform** | Claude Code extension inside Visual Studio Code, running against both local repositories (`domitory_management_backend`, `domitory_management_frontend`) |
| **Access time** | 2026-08-25, 21:27–21:32 (ICT). Corroborated by the commit timestamps of `7ac3ac1`, `a2fcab3`, `46cf538` (backend) and `d11a210`, `9d43fd4`, `14e1539`, `5ab523c`, `1990063` (frontend). |
| **Purpose of use** | To design and implement, end-to-end, a self-service "change password" flow reusable across all three roles (student, staff, admin), following the existing password-hashing pattern already used in `AuthService`. |
| **Content generated by AI** | Backend: `ChangePasswordDto` (`src/auth/dto/auth.dto.ts`) with current/new password validation; `UsersService.changePassword` (`src/users/users.service.ts`), which verifies the current password with bcrypt before rehashing and saving the new one; the `PATCH /api/users/change-password` endpoint on `UsersController`, guarded by the existing `JwtAuthGuard`. Frontend: a shared `ChangePasswordForm` component (`app/components/ChangePasswordForm.tsx`, 115 lines) built to render correctly across layouts with and without a local `:root` theme; three role-specific pages (`app/student/profile/change-password`, `app/admin/profile/change-password`, `app/staff/profile/change-password`) wiring the shared form into each profile area; entry points added to the student and admin layouts, and a new avatar-dropdown account menu (replacing a plain logout button) added to the staff layout so all three roles share the same "Hồ sơ cá nhân / Đổi mật khẩu / Đăng xuất" UX. |
| **Work done independently by the student** | Deciding the feature's shape (one shared form component reused by three routes, rather than three separate implementations); reviewing and testing each generated diff before committing; adapting the staff layout's dropdown menu to match the pattern already used in the admin/student layouts; verifying the bcrypt verify-then-rehash flow against `AuthService`'s existing password logic; committing the 9 resulting commits individually with descriptive messages. |
| **Verification performed** | Manually exercised the change-password flow for all three roles (correct current password, wrong current password, weak/invalid new password) before committing; confirmed the endpoint is unreachable without a valid JWT. |
| **Evidence** | Commits `7ac3ac1`, `a2fcab3`, `46cf538` in `domitory_management_backend`; commits `d11a210`, `9d43fd4`, `14e1539`, `5ab523c`, `1990063` in `domitory_management_frontend` (all authored by `quockhanh2006hkn@gmail.com`, 2026-08-25). |

## A.3. Independent Work and Verification Methods

**Performed by:** Trần Hoàng Quốc Khánh | **Reviewed by:** `Trần Huỳnh Mạnh Đạt` | **Edited by:** Trần Hoàng Quốc Khánh

* **Done entirely by the team, without AI:** final decisions on feature scope for PA5, code review and integration of every AI-assisted diff before commit, and ownership of the completed change-password feature and test documentation.
* **How AI-assisted content was edited:** every AI-generated diff (backend and frontend) was read and manually exercised before being committed; the shared-component approach for `ChangePasswordForm` was a deliberate team-style decision, not an AI suggestion; Spec Kit–generated test cases were only accepted after being checked against the actual running feature.
* **Verification methods:** manual functional testing of the change-password flow across all three roles; commit-by-commit review before push; this report's own content was verified against real Git history rather than written from memory (see §A.2.3.3).
* **Commitment:** every commit hash, timestamp, file path, and document reference in this document was checked against the actual Git history of the three repositories. Where a member's *specific* AI tool usage (prompts, exact tool version) could not be independently confirmed in this session, it is marked "carried over from PA4 declaration, not re-confirmed" (§A.2.1, A.2.4) or left open for the member to complete (§A.2.2) — this document does not assert AI-usage details that were not verifiable.
